# 笔记库 写法框架

本文件是 `self-notes-read` 的**写法披露参考**：形态选型、章节框架、文风表。整理时的操作纪律仍以父级 `SKILL.md`「整理时硬约束」为准。规范只定框架，单篇章节名/表字段/示例数量按主题自定。

何时 Read：新建库文档、改形态/框架、不确定章节怎么摆、写概述/安装/实战结构时读全文。只改文风/精简时读「文风对照」。只做外链收敛且不改结构、不改文风时可只读 `SKILL.md`。

## 书写原则（写法向）

1. **原子化**：单文件打开即可学完该主题，不依赖「请看另一篇」才能理解。
2. **读者是初学者**：术语出现即解释，避免跳步；基础类短文宜短、好扫。
3. **引用内聚**：多层引用合并进同一文件不同模块；禁止指向不存在文档/章节的「见××」。
4. **少元叙述**：少写「本文从零说明…」；直接陈述知识本身；信息密的短段与表优先于空壳小标题。

外链分类、已验证步骤、收敛/文风操作面：见 `SKILL.md` 硬约束（此处不重复含义）。

## 文档头

自有归纳文：

```markdown
> 归纳日期：YYYY-MM-DD

# 标题
```

第三方总结 / 外部文档：

```markdown
> 外部文档
> 来源：https://example.com/原地址
> 归纳日期：YYYY-MM-DD

# 标题
```

* 新建或完成一次归纳整理后写入/更新归纳日期；日期以本行为准，与文件系统修改时间无关。
* 外部文档须保留 `外部文档` 与 `来源`；无明确修改指令时不动正文（纪律见 `SKILL.md`）。

## 按主题选型（先选形态，再套框架）

| 形态 | 适合 | 推荐结构 | 范本感觉 |
|------|------|----------|----------|
| **API / 语法知识文** | 标准库、语言机制、对照选型 | 下文「知识文档框架」四层（可合并，不可颠倒） | `01-Python/05-标准库/Python Re.md` |
| **外部工具 / CLI** | LibreOffice、ffmpeg、Pandoc、系统命令封装 | **概述 → 安装（够细则细）→ 最小试用 → 可复制脚本** | 概述解惑；安装用业务命令 `--version` 验收 |
| **概念综览 / 基础认知文** | 多概念并陈、要建立心智模型（如 Agent / Harness 基础） | 下文「概念综览文框架」 | `09-AI/Harness/010_Agent基础.md` |
| **库 / 框架入门文** | 可 import 的库或编排框架首次入门（如 LangChain、LangGraph） | 下文「库 / 框架入门文框架」 | `012_Langchain.md` / `013_LangGraph.md`（骨架对齐 `010_Agent基础.md`） |
| **问题短文** | 单一排障 | 「问题类文档框架」 | — |

* 不为「有四层」就把工具安装文整篇改成 Re 式四层。
* 一段「概述」说清定位即可；标题叫「概述」或「这篇文档介绍什么」均可，关键是不重复。
* 概念综览文**禁止**只用「出现时间先后」当正文脊柱；时间线是重要块，但只管编年。
* **目录名 ≠ 主题**：归档在某文件夹下，正文仍只服务标题主题；有 API 的库/框架入门文必须带完整代码。

## 知识文档框架

以 `01-Python/05-标准库/Python Re.md` 为范本，**API/语法类**按以下四层（可合并相邻层，不可颠倒）：

```
# 标题（主题 + 范围）

## 概述 / 这篇文档介绍什么   ← 一段话：是什么、解决问题、边界（只写一次）

## 概念                    ← 术语、易混区分；与概述不重复

---

## 核心规则 / 语法 / 机制   ← 速查表为主，最少必要示例

## API / 用法对照            ← 表格横向对比

---

## 实战示例                  ← 按场景分节，不按 API 字母序
```

### 各层要求

| 层级 | 写什么 | 怎么写 |
|------|--------|--------|
| 概述 / 介绍 | 解惑与定位 | 是什么、一般干什么；**手装**依赖可短表或 `###`；**工具/CLI 文**可用 `### 做不到` / `### 被依赖`；概念综览与库入门默认不写「做不到」「不是什么」；不写目录导航套话、安装步骤、调用流程、降级链、随包传递依赖 |
| 概念 | 读懂后文的前置 | 词条式列表；易混点写对比；勿复述概述句子 |
| 核心规则 | 脱离场景仍成立 | **表格优先**；代码只证明一个点，可复制运行 |
| API 对照 | 同类能力选型 | **对比表**；附 1 组最短示例 |
| 实战示例 | 真实任务落地 | **按场景分 `###`**；生产契约与研究/深采分节；交付物写字段表；案例≠整篇主题边界 |

### 写法习惯

* 大模块之间用 `---`；标题层级不超过四级（`#`→`####`）
* 能表格不写长段；能一行注释说清的不写块注释
* 代码块标 `py` / `bash`；示例追求复制可运行
* 同一知识点只在一处展开；实战节引用概念层术语，不重复讲原理
* 生产验证过的复杂案例放实战后部，写清场景即可，不强制「背景/原因/思路」四段式
* 实践脚本块：节内自包含（改硬编码路径即可跑）；去掉无意义类型判断与过度兜底
* **生产契约**与**研究/深采**分 `###`；交付格式须有**字段/列结构表**，与文件清单分开

### 不要（写法向）

* 堆「参考资料」外链代替正文；把 API 逐条抄进正文而无场景
* 为凑「基础/进阶/高级」硬拆；用框架整篇重写已验证安装文
* 「自××迁入」、勾选空话、失效路径关联句
* 把「简洁」执行成删有效步骤或只删不迁；把清晰列表挤成一行
* 「概述」与「是什么」同义反复；概述堆封装/降级/subprocess
* 用 `where`/`which` 代替 `xxx --version` 做安装验收
* 因旧脚本只覆盖部分场景，把标题级主题收成「本篇只讲该场景」
* 只改概述、后文同义表原样；正文写改动留痕或长期「待归纳」中间稿
* 杂烩脚本注释顶替各库案例；把实现依赖写成产品同类
* 单库概述展开目录选型或「见同目录 README」；写随包传递依赖；用「旁路」代替「被依赖」
* 多条信息合成一句；`###` 与裸段落混排；能力表妄称「独有/不支持」；省略版本分界
* 按代码原目录机械归档；新建只含对照表的「工具链」假案例
* 生产与深采混成一条；只列渠道名/文件名却无 path/字段表
* 未确认留档就删仍在管生产仓；对 `> 外部文档` 按本库框架整篇改写

### 文风对照

| 宜 | 忌 |
|----|-----|
| 概念综览按理解梯子排正文；时间线紧接目录 | 正文按出现年份排队；时间线丢文末或代替分层 |
| 叠放关系图全文只留一处 | 「知识分层」与「概念关系」同义双图 |
| 父子概念用 `###` 收入父 `##`；独立标准另开 `##` | 全平级 `##`；或把标准身份抹进父节 |
| 相关概念同块：是什么 → 关系 → 为何 | 同主题多 `##` + 密 `---` 切开 |
| 章节标题用读者熟悉的本名 | 自造「××接入：」类前缀盖住本名 |
| 编号 `###` + 嵌套列表，预览能看出归属 | 长墙段落；或空 `####` 看不出块界 |
| 概述解惑：是什么、干什么、手装依赖 | 「不是什么」专节；概述堆流程、误解纠正、产品栈、封装三步 |
| 标题与主题一致；目录只归档 | 父目录名绑架正文主线；「材料里只有 X」→ 整篇只讲 X |
| 同目录范本先对齐骨架；库文配完整可运行代码 | 「第一次上手 / 认名即可」；课件标外部文档+见同目录 |
| 安装用 `工具 --version` 验收 | 安装节教 `where.exe` / `which` |
| 改概述后扫安装/概念去重 | 只改一处，后文同义表原样 |
| 保留好看易扫的列表 | 为「短」把分条压成一句 |
| 安装写清路径、环境变量、如何验证 | 只剩口号式短句无法落地 |
| 自然语言、有效信息密 | 元叙述套话、空标题、为凑框架灌水 |
| 可核查事实（日期、官方定义、论文锚点） | 「某某 CEO 强调」「某某随后说成」式金句背书 |
| 一句一事；多维对照用表；术语首次白话解释 | 一根长破折号串类型/做法；读完复述不出「是什么/管什么/怎么做」 |
| 越界段并进目标后再删 | 只删不迁，或「待归纳」旁路文件 |
| 正文只有知识与案例 | 「本文件只管」「迁出见某某」「与同目录互补」 |
| 产品定位一句说清；实现依赖用「被依赖」 | 把产品与实现库写成同类工具 |
| 只写需手装的依赖 | 罗列随包传递依赖 |
| `###` 分块 + 统一 `*` 列表 | 加粗冒号小标题、列表与裸段混排、多事一句 |
| 导入名/能力变更写清版本分界 | 「二者等价」不写从哪一版开始 |
| 多库对照写「何时更合适」 | 矩阵乱标「独有 / 不支持」 |
| 外仓按主题并进已有库/工具文 | 新建「工具链」假案例；跟错历史目录 |
| 案例写真实 path/字段表 | 只列渠道名/文件名 |
| 生产与深采分节 | 一个案例里混 mode1 与 mode2/3 |
| 留档确认后再删外仓 | 笔记有影子就删仍在管生产仓 |
| 外部文档留标识+来源，正文近原稿 | 把第三方总结当外链再「归纳优化」；把截图误标成外部文档来源 |

## 概念综览文框架

多概念并陈、要建立「是什么 / 怎么叠」心智模型时用（范本：`09-AI/Harness/010_Agent基础.md`）。与 API 四层文不同：脊柱是**理解与组装顺序**，不是字母序或出现年份。

### 推荐骨架

```text
# 标题
## 概述          ← 读法约定 + 边界（一句说清；不堆第二张分层图）
## 目录          ← 多节概念文必有；锚到正文 ##
## 概念出现时间线 ← 重要：紧挨目录之后；只编年，不决定后文顺序
## …正文各层…   ← 按理解梯子，总框在前
## 概念关系      ← 全文唯一一张叠放图 + 可选组装直觉
```

### 排布硬规则

| 规则 | 做 | 不做 |
|------|----|------|
| **正文脊柱** | 按理解/组装：总框 → 指令 → 进窗 → 动手 → 材料包… | 因「谁先火」把各概念按年份排成正文主序 |
| **时间线** | 目录正下方独立 `##`；表内时间锚点 + 一句话 | 丢文末当可有可无附录；或让时间线代替目录与正文分层 |
| **总框概念** | Agent / Harness 这类「系统形态」放正文最前 | 夹在技法中间，读成又一个平级招数 |
| **父子概念** | 子手段进父节 `###`（如 RAG、Memory → 上下文工程） | 业界/本文已认定「A 属 B」仍拆两个平级 `##` |
| **独立约定** | 有独立标准身份的（如 AGENTS.md / Skills）在相关父主题后另开 `##` | 强行塞进父节抹掉标准身份 |
| **相关必同块** | 如 Function Calling 与 MCP 同一 `##`：A 是什么 → B 是什么 → 关系 → 为何需要 | 拆成多个 `##` 再用密 `---` 切开；「何时支持」另开平行大节 |
| **标题用本名** | `## Function Calling 与 MCP` | 自造前缀如「工具接入：…」盖住读者熟悉的名字 |
| **分层图单一事实源** | 叠放关系**只在一处**（通常文末「概念关系」） | 目录下再贴「知识分层」树与文末同义双图——严重错误 |
| **预览可辨层级** | 编号 `###`；块内 `*` + **粗体词条** + 嵌套列表 | 整墙长段；或空 `####` 占位看不出块界 |

### 块内写法

* 先「是什么 / 和谁区分」，再「为何 / 何时」；附属时间锚点可收进「是什么」下的时间线条目。
* 充实摘录/概要图：有层级地展开；禁止为「一整段」牺牲扫读，也禁止无内容的薄标题堆。
* 合并进父节前须有依据（官方定义、综述分法、或本文已写的归属句）；猜归属先问。

### 不要（概念综览向）

* 概述/目录区与文末各画一张同义梯子
* 把协议层（Tool Calling / MCP）整块并进「上下文工程」只因为「工具描述会进窗」
* 用 `---` 在同一主题的 `###` 之间制造「好几个大章」的观感

## 库 / 框架入门文框架

适合：读者第一次建立对某个**可 import 库/框架**的可用心智模型（LangChain、LangGraph、某 SDK）。与纯概念综览的差别：机制必须落到**完整可运行代码**；与 API 四层文的差别：先按组装顺序立住最小闭环，不先做字母序 API 手册。

范本节奏：同目录概念综览（如 `010_Agent基础.md`）的**骨架** + 本形态的**代码密度**（如 `012_Langchain.md`、`013_LangGraph.md`）。

### 推荐骨架

```text
# 标题（库/框架本名）
## 概述          ← 本文讲清什么；按理解与组装顺序（一句）
## 目录          ← 锚到正文 ##
## Xxx 是什么    ← 客观定义 + 要解决的工程问题（短）
## 核心组件/概念 ← 表：词 → 含义（入门够用即可）
## …机制节…      ← 每一节：定义 → 完整 py 示例 → 要点列表
## 概念关系      ← 全文唯一一张叠放图 + 一句组装直觉
```

无多概念编年需要时，**可不设**「概念出现时间线」。

### 排布硬规则

| 规则 | 做 | 不做 |
|------|----|------|
| **一文档一主题** | 标题是 LangChain 就只写 LangChain | 因在 `Harness/` 下改写 Harness 主线；或把 LangGraph/MCP 写成平行专章 |
| **对齐范本** | 同目录有 `010` 类范本则先 Read 再套骨架 | 另起「三个误解 / 不是什么 / 第一次上手顺序」 |
| **客观是什么** | `**定义**` + 事实表 + 代码 | 「它不是什么」专节；越级「读别人代码时…」 |
| **代码必达** | 每条关键机制旁有可复制运行的完整示例 | 只画文字梯子、ASCII 流程而无 `py` 块 |
| **循序渐进** | 最小线性例子 → 再分支/检索/工具 | 一上来产品栈选型、升级信号、开箱 Agent 全家桶 |
| **材料转换** | 课件/截图要点写入自有正文 | 外部文档头、图片来源句、文内嵌原图充来源、「见同目录」 |

### 块内写法

* 先定义，再给**一整段能跑的代码**（import、对象构造、`invoke`/`compile` 等闭环），再补三点以内的读码要点。
* 示例参数硬编码在代码里；用模拟检索/本地函数代替重依赖，仍须语法完整。
* 与相邻库的对照表：只服务「本主题边界」（如 LangChain Tool vs MCP Tool 一行表），不展开邻库教程。

### 不要（库/框架入门向）

* 用当下营销口号（如一律「Agent = Model + Harness」）替换该库 historically/实务上的组件与编排主线，除非本文主题就是 Harness
* 在入门文写「第一次该抓住什么」检查清单式元教学（完成标准应体现在读者能复述并看懂示例，而不是另开行动清单章）
* 无用户授权时把第三方课件标成 `> 外部文档` 却又整篇按本库文风改写——要么近原稿保留外部标识，要么转成自有归纳文且去掉来源耦合

## 问题类文档框架

适用于「解决某一具体问题」的短文：

```
## 背景
## 要解决的问题
## 思路
## 实际案例
```

给出可复现的最小示例即可。

## 与其它形态的关系

| 形态 | 规范位置 |
|------|----------|
| 单文件分阶段脚本 | `python-standard-coding` → `references/script.md` |
| 多文件 Python 项目目录 | `python-standard-coding` → `references/project.md` |
| 从外部项目抽协议写爬虫 | 落地切步仍 `python-standard-coding` → `references/script.md` |
| 何时读笔记、整理纪律、**本写法框架** | `self-notes-read`（本文件属其披露参考） |

知识库 `.md` 只记可复用知识与场景，不把工程 skill 里的规范再抄一遍。

## 案例目录（笔记库 `cases/`）

目录名与案例内文件名优先英文（`company_background`、`01_case.md`）；标题可用中文括注。写入案例时去掉内网地址、发群、OSS 等生产环节和密钥。

可跑案例的笔记：实战节写字段表，摘录一次实测的块数、id、路径；入口脚本放在案例目录，与摘录同一份产物。可核对语料：公开通告、判决、年报，文首写检索词。跨文档或多跳：几篇输入出现同一批实体。
