# 改已有 skill

用户说「改一下这个 skill」「skill 里补一条」「这个 skill 不管用」时走这一份。

## 1. 读全再动

读目标 `SKILL.md`、它指向的 `references/`，以及提到它的其它文件：

```powershell
Select-String -Path skills\*\SKILL.md,skills\*\references\*.md,CONTEXT.md,skills-list.md,docs\*.md -Pattern "<skill 名>"
```

**完成标准**：报得出「要改的这条内容现在写在哪几处」，一处一行号。

## 2. 判该不该加

按 `SKILL.md` 第 1 条：会重复发生 **且** 模型默认不会做。模型默认就照做的指令是废话指令，花常驻成本换零行为改变，不写。

## 3. 给对照，等点头

按 `SKILL.md` §4：先把「改哪一处、改前、改后、为什么」连同「落哪、为什么落那」摆给用户，点头再动笔。

**完成标准**：每处改动都有一组「改前 / 改后 / 为什么」（原文没有这条的写「原来没有」），且用户已明确同意。

## 4. 改

- 先读文件再改，改的时候 `old_string` 从刚读到的输出里复制，别凭记忆重写。
- 同一个文件的多处改动一次改完，不要连发几次小改。
- 同一含义只改一处。改了叫法就全局改，留半套新名比不改更坏。
- 解释为什么，少堆 MUST。
- 一处内容改到读不懂时，回头按 `references/style.md` 的层级重排，别硬塞。

## 5. 从反馈泛化，别贴着例子写窄

用户手上只有两三个例子，规则要能用在没见过的情况上。三条判据：

- **别过拟合**：只对那几个例子有效的改法等于白写。顽固问题换个说法、换条路径试，比堆一堆 MUST 便宜。
- **看过程，不只看产出**：产出对但过程绕远，说明正文里有一段在浪费它的时间，删掉再跑一次看结果。
- **把重复劳动收进 `scripts/`**：几条路径里各自写了同一段脚本，就写一份放进 `scripts/`，正文改成调用它。

## 6. 连带文件同轮改完

按 `SKILL.md` §5 那张表逐项过一遍，同一轮改完，不攒到下轮。

## 7. 验

- 脚本层：`python skills/self-skill-crud/scripts/validate_skill.py skills/<name>`。
- 对照实验：**改写的或新增的**规则至少过一轮，照搬原文的不必（照搬不新增判断）。做法：同一个任务跑两臂——对照臂只给任务，实验臂多给被实验的那条规则原文，比两臂差异。它是自检、降低出错概率；不判规则有用性，真实使用更复杂，以后出错也不推翻这一轮。
- 动了 description 就另验触发：造 20 条查询，一半该触发一半不该触发，不该触发的那些贴着实例写（别写成一望而知的远例）。给用户过一遍再定稿。这一步靠人判，没有自动化脚本。

## 8. 什么时候算改完

用户确认新文本可用；脚本通过；对照实验留了记录；连带文件已改。

回报按 `references/style.md` 的「改动怎么给人看」写成三行（改前 / 改后 / 为什么），别贴行号、别贴整篇。第 3 步已经给过一轮，这里是落盘后的确认。

停止条件三条任一成立就停，别无限迭代：用户说满意 / 反馈全空 / 再改没有实质进展。
