# Python 测试：选定测试边界 → 写进 spec → 写 pytest

这是三个不同的问题，缺哪一步都会白写测试：

| 问题 | 谁回答 | 产物 |
|---|---|---|
| 在哪测 | 选定测试边界（seam） | 一张边界清单，且用户确认过 |
| 测什么、谁跑 | spec 的 Testing Decisions 一节 | 写进项目文档，不再每轮口头问 |
| 怎么写 | pytest 模式 | 用例代码 |

只有第三步、没有前两步，产出的是「测了实现、一重构就红」的测试；只有前两步、没有第三步，spec 落不了地。

## 第 1 步：选定测试边界

**测试边界（seam）**= 你观察行为的那个公开边界：不伸手进去就能验的接口（HTTP 端点、公开函数、CLI 入口、契约字段）。测试只落在边界上，绝不落在内部结构上。

先摸底再动笔：

1. 读项目的术语表（本仓是 `CONTEXT.md`）与相关 ADR——测试名与断言要用项目自己的词，改名一次要全链一起改。
2. 列候选边界。**优先用已有的边界，不要新增**；非要新增，就选尽可能高的层次（靠近用户可见入口，而不是内部模块）。
3. 边界越少越好，理想是一条。

**把边界清单交给用户确认，这条没有例外：用户没点头的边界，一条测试都不写。**

每条边界都要判**低成本还是高成本**，判据是跑一次付出什么：不联网、不起服务、不调模型的边界成本最低，每次改动都跑；要起服务、要联网、要花钱调模型的边界成本高，留给人在关键节点跑。这个判断就是后面「谁跑」的依据，所以第 1 步必须做，不能推到验收时再想。

完成标准：边界清单每条都写明了「验什么」+「跑一次要付出什么（是否联网 / 起服务 / 调模型）」，且用户已确认。

## 第 2 步：把结论写进 spec 的 Testing Decisions

边界定了就固定下来写进项目文档，别每轮重新问一遍。模板见 [references/spec-template.md](references/spec-template.md)；测试相关的部分至少覆盖：

- 哪些模块被测、在哪条边界上测
- 每条边界验什么行为——用项目术语写成规格的样子，不写实现
- 现有代码里可参照的同类先例
- 这条边界跑一次需要什么（联网 / 服务 / 模型），因此**谁跑**：能全自动的归自动跑（CI/本地），高成本的归人

完成标准：文档里能直接回答「这次改动，哪条边界我跑、哪条边界人跑、各自验什么」，不需要再问一遍。

## 第 3 步：按一条用户路径写 pytest

### 动笔前先定环境与存放位置

**用项目自己的环境跑，不要临时开一个。** 项目根、`.env`、README、运行手册里写着它用哪个解释器（conda 环境名或 venv 路径）。测试进程与业务进程用同一个环境最省事；分开也行——黑盒测试只需要 pytest 加一个 HTTP 客户端，不必装齐业务依赖。

**缺包就问，不要自己装。** 环境里缺测试要用的包时，把「缺什么、为什么需要、装它的命令」一次说清，交给用户决定。用户没答应就不装。

**落盘用例先借项目已有的目录夹具，别用 `tmp_path`。** 它建的目录带 `0o700`，受限权限下收集阶段就 `PermissionError`。动笔前先翻项目 `conftest.py`；没有才补一个不带 mode 的建法（见 `agent-dsh.md` §5）。

**环境不全就不测。** 解释器、依赖、被测服务任一不齐，说明缺什么然后停下；不要把「跑不起来但测试先写了」当成交付。被测服务尤其容易想当然——先真打一次健康检查确认它在应答，别假设它起着。

**跑给谁看，就按谁能看懂来写。** 让用户执行的验证，交付时必须连带三件事：**前置健康检查**（会话级夹具先打一次健康检查，服务不应答就当场用一条可读消息失败，而不是让几十条用例各等一次超时）、**超时量级**（本地口一秒内返回就别写 120 秒——长超时等于把静默等待外包给用户）、**跑测记录落盘**（每条用例的「这条在测什么」、用时、最慢几条、全量清单落盘）。跑完只给「满屏 F 加一个数字」，等于没交付。

### 测试文件写到哪

放 pytest 官方约定的 `tests/`；项目已有测试目录就跟着它，不要另起名字。

写之前先看项目自己的自查与 CI 脚本会不会扫到这个目录：不少项目的结构检查会遍历源码目录、并假定每个顶层目录都是一种分层，新开 `tests/` 会让它报错甚至崩溃。这种情况要**一并处理**——让那个检查把 `tests/` 当非生产目录跳过——而不是为了绕开它把测试塞进 `scripts/` 或改名躲开。

**一次一条能力路径**：一条测试 → 一点实现 → 再下一条。不要先写一堆测试再写实现——那验的是你**想象中**的行为，你会先定死测试结构再去理解实现。

每条路径走红 → 绿：

1. 先写会失败的测试（红）。跑一次，确认它是因为「功能还没做」而失败，不是因为你写错了。
2. 写刚好让它通过的最小实现（绿）。
3. 不预告未来的测试，不加臆测功能。

断言只落在边界上。**预期值要有独立基准**——已知正确的字面量、手算样例、spec；不要用代码同样的算法再算一遍，那样它必然通过，永远不可能和代码不一致。也别照文档或实现的**措辞**写断言：文档说「会说明被忽略」、代码写的是「不消费」，抠文案的那版测试就误红了，而行为其实是对的。断言行为，不抄用词。

### 一条用例 = 一个用户可见事实

主断言写**业务事实**：这份 CSV 出来是三列、这份 PDF 是十页、这条失败带的是哪个降级码、超限时命中哪条上界。状态码、`error is None`、`content` 非空这类**只作附加断言**——它们区分不了「做对了」与「没炸」。反向断言要成对（「超限时报 X」配「不超限时不报」），否则一个恒报的实现也能全绿。

### pytest.ini 第一版就带超时强杀

- 环境：第一次建 `pytest.ini` 时（`markers` 与 `--strict-markers` 也在这一份里）。
- 场景：用例或收集阶段卡住不返回——进度停住不动、没有任何提示，进程一直占着，没人会发现。
- 操作：`faulthandler_timeout = 300` + `faulthandler_exit_on_timeout = true`：到点打印所有线程的栈，再结束进程。默认 300 秒；确有单条用例要跑更久，就整体调大并在同一行写清为什么。
- 步骤：这两行写进 `pytest.ini`。导入 / 收集阶段就卡住时再加外层：`python -c "import faulthandler, sys, pytest; faulthandler.dump_traceback_later(300, exit=True); sys.exit(pytest.main(['tests', '-q', '-s']))"`——栈打在 stderr，而 pytest 默认把输出捕获走，所以带 `-s`。

### 能力类别标记：可追踪、可按类跑

一条用例 = 一个能力类别下的一个覆盖点。每条打一个 `@pytest.mark.capability_<类>`（单一类别的文件用模块级 `pytestmark`，混合文件逐条打），类别登记进 `pytest.ini` 的 `markers` 并开 `--strict-markers`——于是能 `pytest -m capability_epub` 只跑一个类别。

**汇报按「能力类别 × 覆盖点」，不按条数。** 十三个扩展名各一条不是十三个能力，是一个能力的十三个覆盖点；清单驱动的参数化允许，但 docstring 要写明它覆盖的是「清单里的每一项」。

### 交之前按能力类别去重

**同一能力只在最靠近它的那条边界验一次。** 端到端边界（HTTP / CLI）只抽查两三个代表，证明真实服务走得通；完整矩阵留在成本最低的那条边界（不联网、不起服务的那个）。同一能力的同一个可观测结果出现两次，就是重复覆盖。

交之前做一次**重复覆盖扫描**：把现有用例按 `(能力类别, 可观测结果)` 两列分组，同组多于一条就问「哪条离能力本体更近」，把远的删掉或合并。删完要能说清「能力覆盖一条没少」——条数下降、覆盖不减，才是去重而不是砍覆盖。

- [references/pytest-patterns.md](references/pytest-patterns.md) —— fixtures、参数化、异常、异步、标记、覆盖率、目录组织
- [references/pytest-details.md](references/pytest-details.md) —— 更细的模式与配置
- [references/pytest-advanced.md](references/pytest-advanced.md) —— monkeypatch、临时文件、数据库、freezegun、并发、基于性质的测试

完成标准：新测试跑绿；并且**把实现整体重写一遍（行为不变）测试仍然绿**——这是「测试没与实现耦合」的唯一硬证据。

## 第 4 步：交之前过一遍反模式

命中任一条就改：

- **与实现耦合**：mock 了内部依赖、测了私有方法、或绕过接口从侧面查（直接查库而不走接口）。特征：重构后行为没变，测试却红了。
- **自证式断言**：断言把预期值按代码同样的方式重算一遍，或断言一个常数等于它自己。特征：必然通过。
- **横向铺开**：先写完所有测试再写实现。特征：测试验的是东西的**接口形态**，不是行为。
- **只走 happy path**：没有一条断言失败行为、边界或降级路径。
- **重复覆盖**：同一能力的同一个可观测结果在两条边界里各验一遍。特征：两条里删掉任意一条，覆盖没有变化。
- **只断言状态码**：主断言是 200 / 非空 / `error` 为 None，实现退化成空转也照样绿。特征：把返回值改成「总是成功」测试仍全绿。

完成标准：每条都能说出「本轮的测试为什么不犯它」。

## 边界

- 不宣布「测试写完了」：先跑一次。没跑过的测试不算验证。
- 不为了迁就测试去改行为。测试红了先判是实现错还是测试错。
- 不把高成本边界塞进自动跑：会联网、起服务、调模型、花钱的验证，写明由人跑。
- 动了测试基础设施（`conftest`、`pytest.ini`、共享夹具）之后，**先全量跑一次再交付**：夹具被改坏时只有全量跑会以「一片 ERROR」的形式暴露，静态审查看不出来。
- 不为让门禁数字好看而删用例：覆盖率掉了先查原因，不许删断言、改预期值、把不通过的 `skip` 掉（见 `code-principles` 第 13 条）。
- 本 skill 只管 Python / pytest。前端测试另说。
