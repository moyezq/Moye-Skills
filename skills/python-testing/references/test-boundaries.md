# 测试驱动开发（Test-Driven Development）

TDD 就是「红 → 绿」循环。本 skill 是这样一份参考：让这个循环产出值得留下的测试：什么是好测试、测试放在哪里、反模式，以及循环的规则。每一节在每一轮循环都适用：在循环之前和循环之中查阅它们，而不是在循环之后。

在探索代码库时，读项目自己的术语表，让测试命名和接口用词与项目的领域语言保持一致，并尊重你正在改动的区域里的 ADR。

## 什么是好测试

测试通过公开接口验证行为，而不是验证实现细节。代码可以完全改变；测试不应该变。好测试读起来像一份规格说明：「user can checkout with valid cart」明确告诉你存在什么能力，而且它能在重构（refactor）后依然成立，因为它不关心内部结构。

示例见 [good-tests.md](good-tests.md)，mock 指南见 [mocking.md](mocking.md)。

## 测试边界（seam）：测试放在哪里

**测试边界**是你在其上做测试的公开边界：一个让你无需深入内部就能观察行为的接口。测试都待在边界上，绝不针对内部实现。

**只在事先约定好的边界上做测试。** 写任何测试之前，先写下待测的边界，并与用户确认。不在未确认的边界上写测试。你不可能测试所有东西，所以事先把边界约定下来，测试投入才会落在关键路径和复杂逻辑上，而不是每一个边界情况上。

问：「公开接口是什么，我们应该测哪些边界？」

## 反模式

- **与实现耦合（implementation-coupled）**：mock 内部依赖、测试私有方法，或者绕过接口查（查数据库而不是走接口）。识别标志：你重构之后测试就挂了，但行为并没有变。
- **自证式断言（tautological）**：断言用和代码一样的方式重新算出期望值（`assert add(a, b) == a + b`、手工按同样方式推导出来的快照、把一个常量断言为等于它自己），于是它必然通过，永远不可能和代码不一致。期望值必须来自独立基准：一个已知正确的字面量、一个算过的例子、规格说明。
- **横向铺开（horizontal slicing）**：先把所有测试写完，再写所有实现。批量测试验证的是_想象出来的_行为：你测的是东西的_接口形态_而不是面向用户的行为，测试变得对真实变化不敏感，而且你在还没理解实现之前就先锁死了测试结构。改用**一次一条能力路径**：一个测试 → 一个实现 → 重复，每个测试都是一条**通程样例（tracer bullet）**，回应上一轮循环教会你的东西。

## 循环的规则

- **先红后绿。** 先写失败的测试，然后只写足够让它通过的代码。不要预判未来的测试，也不要添加臆测功能。
- **一次一条能力路径。** 每轮循环一条边界、一个测试、一个最小实现。
- **重构不属于循环的一部分。** 它属于评审阶段，而不是「红 → 绿」的实现循环。
