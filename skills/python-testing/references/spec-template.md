# spec 模板

它把一轮对话的结论固化成文档，所以有争议的东西只需要问一次。**不做访谈**：已经聊清楚的直接综合，缺的才问。

## 做法

1. 先探仓库，弄清现状。全篇用项目自己的术语表词汇，相关区域的 ADR 要遵守。

2. 画出你打算在哪些测试边界上测这个功能。**已有的边界优先于新增**，选尽可能高的层次（靠近用户可见入口）；要新增也提在最高层。全仓的边界越少越好，理想是一条。

3. 拿边界清单跟用户对一遍，确认与他的预期一致。**没对上就不要往下写。**

4. 按下面的模板写 spec，然后发到项目文档的既定存放位置。`进一步说明` 一节可以留空。

## 模板

```
## 问题陈述

用户视角下的问题：他现在遇到的是什么。

## 方案

用户视角下的解法：做完之后他能做什么。

## 用户故事

一长串编号的用户故事，每条写成：
1. 作为 <角色>，我要 <功能>，以便 <收益>

例：
1. 作为手机银行客户，我要看到我账户的余额，以便对花销作出更有依据的判断

这一节要尽量铺开，覆盖这个功能的各个方面。

## 实现决策

已定下的实现决策，可以包含：要新建/修改哪些模块、这些模块会给出去什么接口、
开发过程中明确的技术取舍、架构决策、schema 变更、API 契约、具体的交互。

不要写具体文件路径和代码片段 —— 它们很快会过期。

例外：如果原型里的某个片段比散文更精确地编码了某个决策（状态机、reducer、schema、
类型结构），把它内联进对应的决策里，并简短注明它来自原型。只留决策密集的部分，
不要放一个能跑的 demo。

## 测试决策

已定下的测试决策，包含：

- 什么算好测试（只测外部行为，不测实现细节）
- 哪些模块会被测
- 同类先例（代码库里已有的类似测试）

本仓补一条必须写清楚的：每条测试边界跑一次需要什么（联网 / 起服务 / 调模型 / 花钱），
因此由谁跑 —— 能全自动的归自动跑（CI/本地），高成本的归人。

## 不在范围内

这个 spec 明确不做什么。

## 进一步说明

其它需要交代的东西。
```
