# 文档地图：建/读/改/遵守

本文件是 `project-docs` 的按需参考。主文件只留职责表；来这里查某一份文档怎么用。

已存在的文件才谈「必须照做」。没建的文件不要假装它在。

---

## CONTEXT.md

规范名称。格式见 [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md)。

- **建**：第一个本项目特有术语落定时。
- **读**：给字段/类/函数起名之前；用户用了一个可能冲突的词时。
- **改**：规范名称定了，或代码让定义过时（例如知识块仍写「用于向量检索」）。同一轮改，不要攒着不改。
- **遵守**：代码和其它文档用术语表里的词，不另造同义名。
- **不要**：写实现细节、开关名、怎么跑。实现细节是 `pipelines.md`，怎么跑是 README。

## docs/adr.md

真正关键的架构决策：现在为什么这样选。格式见 [ADR-FORMAT.md](./ADR-FORMAT.md)。

- **建**：第一条值得记的决策时。不要建 `docs/adr/` 目录。
- **读**：读仍有效的为什么。写代码前按 `architecture.md` 和 `AGENTS.md` 执行。不要把已从本文删掉或挪走的选定当禁令。
- **改**：原则上只追加。明显过期、重复、与新决策冲突时才动已有条目：会影响新决策判断 → 删除（不进 history）；过时但仍能提供有效信息 → 挪到 `history.md`；同一条还活着只改细节 → 重写该条并改日期。现状句只写实现进度。推翻旧决定的那一轮：旧条处理完、`architecture.md` 改完，`AGENTS.md` 有引用也改完。
- **遵守**：不把刻意偏离「修」回常见做法。以本文里**现在**那条为准。
- **不要**：一决策一个文件；用现状句写新选定；只加新条却让冲突的旧选定留在本文。

## docs/history.md

过时但仍能提供有效历史信息的决策。格式见 [ADR-FORMAT.md](./ADR-FORMAT.md)「history.md」。

- **建**：第一次把过时决策从 `adr.md` 挪出时。
- **读**：只在问「为什么曾经那样 / 要不要恢复旧决策」时读。
- **改**：按时间追加。不要把 history 里的选定改回现行法；要恢复就写新 ADR。
- **遵守**：不要把本文当现行法。
- **不要**：把会影响新决策判断的冲突旧条塞进来（那种从 adr 直接删）；不抄旧全文。

## docs/architecture.md

核心功能是什么、核心模块有哪些、哪些暂时或明确不做。格式见 [ARCHITECTURE-FORMAT.md](./ARCHITECTURE-FORMAT.md)。

- **建**：多入口 / 多模块 / 对照实验环境，动手写代码之前。
- **读**：加模块、改目录、按设计写下一批代码之前。读的是目标架构，不是本轮要实现的范围。多个系统组合时，先找该系统自己那一节。
- **改**：核心功能、模块清单、暂时/明确不做变了，同一轮改。模块从「未做」变成「已实现」或「内联」时同一轮改状态。
- **遵守**：新代码进预定目录，不另起一摊。明确不做就是不做。第一条可跑通路径不是终点。
- **不要**：另建 `PROJECT-SPEC.md` 或 `ARCHITECTURE.md`。不要把几个系统揉成一层流水线（系统间通信除外）。不要把现状图写进本文（最小视图）。不要把主流程逐步实现抄进来（`pipelines.md`）。

## docs/pipelines.md

主流程实现细节：各层、各模块、各方法里真正要紧的怎么做。格式见 [PIPELINES-FORMAT.md](./PIPELINES-FORMAT.md)。

- **建**：主流程能按层/模块讲清，且细节不该挤进 `architecture.md` 时。
- **读**：改某层某模块的处理路径、判定、上限、字段落点之前。
- **改**：那些实现细节变了，同一轮改对应段落。
- **遵守**：按现在写的路径与判定改代码，不用已废模块名。
- **不要**：再抄一遍模块树、`.env.example`、OpenAPI；写「原来/现在」对照。

## docs/engineering.md

本仓业务流程里真实踩过的工程问题。一条一个完整事件，问答呈现。格式见 [ENGINEERING-FORMAT.md](./ENGINEERING-FORMAT.md)。

- **建**：本仓出现过至少一条真实工程事故，且这条事故的判据还不在通用 skill 里。
- **读**：问「这个仓工程上踩过什么、后来定在哪」时读。写代码仍按 `architecture.md`、`pipelines.md`、`AGENTS.md`。
- **改**：又踩到一条通用 skill 管不到的事故，同一轮追加。不要把已由 skill 规定的写法再抄进来。
- **遵守**：通用规范已经写成 skill 的，按 skill 做，不把本文当第二份规范。
- **不要**：建成空文件；写成面试题；把 README 章节、ADR 形态、启动入口命名、配置分类再讲一遍。

## docs/overview.md（最小视图）

现状可视化。选型见 [SHOW-FORMAT.md](./SHOW-FORMAT.md)。不是目标架构文档。落盘规则见主文件「最小视图」。复杂界面用 `docs/overview.html`。模块用 `docs/<模块名>-overview.md`；脚本用同级 `<文件主名>.overview.md`。

- **建**：clone 无图且用户要看结构；或用户要求留下场景 2/3 的视图。
- **读**：已有则讲结构前先看，避免另画一张互相矛盾。
- **改**：现状变了且用户要更新图，覆盖同一文件。
- **遵守**：讲现状以这份为准；目标架构仍按 `architecture.md` 执行。
- **不要**：写进 `architecture.md`；可交互仪表（官方 `canvas`）；场景 2 当轮解释默认落盘；无路径的场景 3 往工作区写 `docs/`。

## README.md

给人上手跑。人读结构与禁区见 [README-FORMAT.md](./README-FORMAT.md)（单一事实源）。仓目录怎么摆见主文件邻域入口；若别处仍写旧「四块 README」，以本文与 README-FORMAT 为准。

- **建**：第一条可跑通路径之后，或用户要使用指南。
- **读**：告诉用户怎么跑之前；改端口、入口、环境名之前；写或改根 `README.md`、用户嫌难读时必读 README-FORMAT。
- **改**：端口、入口脚本、环境、密钥怎么注入、完整能力怎么配——和代码同一轮；改完按 README-FORMAT 硬规矩扫一遍。
- **遵守**：按它写的方式跑。运行参数在文件顶部常量区就不要假装有 CLI 参数。
- **不要**：当术语表、目标架构文档或 `docs/` 索引用；用「详见 docs」代替关键步骤；把扩展写成可有可无装饰；写还没验证的方案；写会随需求经常变的前端交互边界。未定方案写进计划类文档。

## AGENTS.md

本仓给 AI 的硬规矩：禁止的库、本仓例外、不能自由发挥的点。

- **建**：全局 `self-*` skill 管不到、且本仓会反复踩的禁令出现时（例如禁止某废弃 SDK、禁止把密钥写进仓、禁止给本仓发明 CLI）。
- **收两样**：本仓例外，加上**反复要用的检查落在仓内哪一处**——回归比对、指纹、结构扫描这类第二轮还要再跑一遍的东西写成仓内的测试或脚本，别每轮现写一个临时文件。这一条只在本文件（或它指到的路径）里定目录位置，换仓就换目录位置。
- **读**：本仓写代码之前（文件存在就读）。
- **改**：新的本仓禁令拍板时；某类检查的目录位置定下来时。
- **遵守**：本文件压过「换个更流行的库」的冲动。编码风格仍走通用 Python 规范，本文件只写**本仓例外**。
- **不要**：把全局 skill 抄进来；没有例外就不要建空文件。

## DESIGN.md

配色、间距、基础交互。

- **建**：UI 超过「一页提问 + 简单 POST」；或用户要定视觉 / 交互规范。
- **读**：改布局、颜色、间距、交互之前。
- **改**：设计 token 或基础交互变了，与界面改动同一轮。
- **遵守**：界面改动跟它走。
- **不要**：单页简单问答为「完整」而建一份设计系统。

## todo.md

本阶段打算做的方向。格式见 [TODO-FORMAT.md](./TODO-FORMAT.md)。权威仍是目标架构文档；本文件不是设计稿、不是工单。

- **建**：已有 `architecture.md`，并且出现第一条本阶段打算做的方向。没有目标架构就不要用 todo 当设计。
- **读**：看现在可能干什么；给「下一步」或新方向提建议时。未点名不按清单改代码。
- **改**：人点名「下一步」。Agent 勾选已完成、在三类节补后续方向。改已有措辞或删行先问。已勾的定期清掉。做成了目标架构里的模块时，同一轮改 `architecture.md` 状态。
- **遵守**：只收本阶段开放项。与 `architecture.md` 里明确不做 / 暂时不做冲突的句子不进本文件。
- **不要**：把明确不做、暂时不做、以后再做写进来；一条写成验收计划和方案；未点名就把清单从上做到下。

## 不要另建：PROJECT-SPEC.md

产品目标与「这次绝对不做」写在 `docs/architecture.md`（核心功能 + 暂时/明确不做）。用户要产品规格时读那一份，不要拆第二份规格。

## 不要放进 `docs/` 标准四份

标准四份只有 `adr.md`、`history.md`、`architecture.md`、`pipelines.md`。不要为「完整」再堆接口手册、运行手册、扩展手册、组件规范、页面结构、部署手册。接口看运行中的 OpenAPI 与 README 的 `curl`；配置看 `.env.example`。`engineering.md`、`todo.md` 与最小视图一样按需：有真实事故再建踩坑文；有本阶段方向再建待办。不要为完整预建。已有仓里多出来的那些文件可以留着，新建仓不要主动建。
