# ADR 格式

真正关键的架构决策写在 **`docs/adr.md`**：一份文件，按 `ADR-NNNN` 编号，每条带日期。不要建 `docs/adr/` 目录，不要一决策一个文件。

`adr.md` 只回答「现在为什么这样选」。核心功能、模块、不做 → `architecture.md`。主流程怎么实现 → `pipelines.md`。本仓 AI 禁令 → `AGENTS.md`。

## 原则上只增加

新的值得记的决策：新编号，追加在文末。

已有条目默认不动。只有这三类才改：

| 情况 | 做法 |
|------|------|
| 明显过期、重复、或与新决策冲突，**且会影响对新决策的判断** | 从 `adr.md` **删除**，不进 `history.md` |
| 过时，但留下仍能提供有效历史信息 | 从 `adr.md` 挪到 `docs/history.md` |
| 同一条还活着，只改细节（默认值、落点、实现） | 重写该条并改日期，不要另开编号 |

编号：扫 `docs/adr.md` 里已有的 `ADR-NNNN`，取最大编号加一。已删编号不复用。

## adr.md 模板

```md
# 架构决策（现行）

仍有效的为什么。

## ADR-0001 · YYYY-MM-DD · {短标题}

{1-3 句：背景是什么、决定了什么、为什么。}
```

就这些。开头只说本文干什么，不要挂一串指针。一条可以只有一段。日期是该条**最后一次重写**的日期。

可选：决策没变、实现进度还值得记时加一行 `现状：…`。只写做没做完。不要写新选定，不要写新禁令。

## history.md

过时但仍能提供有效历史信息的决策。按时间追加。不把旧全文抄进来。全文留 git。

每条一两段说清：当时为什么那样、后来为什么不再现行、后继若有（`ADR-NNNN` 或「无后继」）。

第一次需要挪出过时决策时再建。只在问「为什么曾经那样 / 要不要恢复」时读。不要把 `history.md` 里的选定当现行法。

## 自我更新完成标准

本轮代码或新 ADR **推翻**了某条决定，同时做完才算完成：

1. 旧条已从 `adr.md` 去掉、重写、或已挪到 `history.md`（按上表选一种）。
2. 该进 `history.md` 的已追加；该删的没有留在 adr 也没有留在 history。
3. `architecture.md` 已改（若动到核心功能 / 模块 / 不做）。
4. `AGENTS.md` 若引用了旧规则，也已改。

只加新条、或只改进度说明，不算完成。

## 何时建议记 ADR

三条同时成立才记：

1. **难逆转**：日后改成本有意义
2. **没上下文会费解**：未来读者会看着代码想「为什么偏要这么做？」
3. **真实权衡的结果**：有真实备选，为具体理由选了其一

好逆转就跳过；不费解就没人会问；没有真实备选就只剩「做了显而易见的事」。

### 什么值得记

- **架构形态**：「用 monorepo。」
- **上下文间的集成模式**：靠领域事件通信，不走同步 HTTP。
- **带锁定的技术选型**：换掉要花一个季度的库、总线、鉴权、部署目标。不是每个依赖。
- **边界与范围**：「不做什么」和「做什么」同样值钱。
- **对显而易见路径的刻意偏离**：合理读者会假设相反的任何事。
- **代码里看不见的约束**：合规、合作方契约。
- **不明显的被否备选**：否则半年后有人又提被否的那个。
