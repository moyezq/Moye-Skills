# architecture.md 格式

`docs/architecture.md` 是目标架构文档：模块、数据流、目录位置、状态。不是术语表（那是 `CONTEXT.md`），不是「为什么」（那是 `docs/adr.md`），不是使用指南（那是 README）。写代码时本文与 `AGENTS.md` 是现行约束；`adr.md` 只解释仍有效的为什么。

产品目标与「这次绝对不做」写在本文第 1 节，不要另建 `PROJECT-SPEC.md`。文件名就是 `docs/architecture.md`，不要再写一份 `ARCHITECTURE.md`。

## 何时建

**建**：多入口、多模块、对照实验环境、跨会话迭代。动手写代码之前写出目标模块与目录位置。

**不建**：单文件分阶段脚本；已经选定「单一短链路、一个业务文件」的小 HTTP 服务。

## 必有节

1. **系统是什么**（一两句）加 **明确不做**（产品边界写在这里）。
2. **目标架构模块**：清单或文字表。画的是目标，不是本轮要实现的。可视化现状走最小视图（`docs/overview.md` 等），不要把图写进本文。
3. **目录位置**：每个目标模块现在或将来落在哪个路径。首批实现可以内联，但预定目录要有名字。
4. **状态标记**（每模块一条）：已实现 / 内联 / 未做 / 明确不做。

状态含义：

- **已实现**：代码里有，且位置与目标架构相符（哪怕还糊在同一个脚本里）
- **内联**：逻辑上已有，但尚未按模块拆开
- **未做**：目标架构有，代码没有
- **明确不做**：目标架构文档里出现只为标明边界

## 可选节

只在真能增值时加：离线/在线数据流、数据契约、还缺什么（第一条可跑通路径之后还剩什么，不要把已完成项再写成待办）。

## 同一轮改

本轮代码让某模块从「未做」变成「已实现」或「内联」，同一轮改状态表。旧 JSON / UI 未暴露之类写进还缺什么，不要把状态改回「未做」。
