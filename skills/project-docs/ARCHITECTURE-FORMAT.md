# architecture.md 格式

`docs/architecture.md` 写三件事：

1. **核心功能是什么**
2. **核心模块有哪些**
3. **哪些功能暂时不做或明确不做**

不是术语表（`CONTEXT.md`），不是「为什么」（`docs/adr.md`），不是主流程实现细节（`docs/pipelines.md`），不是使用指南（`README.md`）。文件名就是 `docs/architecture.md`，不要再写一份 `ARCHITECTURE.md`。不要另建 `PROJECT-SPEC.md`。

开头只说本文干什么，不要挂一串指针。只用清单和文字；图走最小视图。

## 何时建

**建**：多入口、多模块、对照实验环境、跨会话迭代。动手写代码之前写出核心功能、核心模块、暂时或明确不做。

**不建**：单文件分阶段脚本；已经选定「单一短链路、一个业务文件」的小 HTTP 服务。

## 必有节

1. **核心功能**（一两句）加 **暂时不做 / 明确不做**。
2. **核心模块**：树或清单。每个模块一句职责。落点可以写在模块旁。画的是目标，不是本轮要实现的范围。

多个系统组合在同一仓库：**每个系统单独一节**写自己的功能、模块、不做。只有「系统之间怎么通信」才写在共享节，不要把几个系统揉成一层流水线。

状态若要标：已实现 / 内联 / 未做 / 暂时不做 / 明确不做。本轮代码让「未做 / 暂时不做」变成已有能力，同一轮改状态。

## 可选节

只在真能增值时加：系统间通信、依赖方向。不要把 pipelines 里的逐步实现、字段形状、开关矩阵抄进来。
