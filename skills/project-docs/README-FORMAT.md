# 根目录 README.md 写法（给人读）

写或改仓库根 `README.md`、或用户嫌 README 难读时读本文。  
建/读/改时机见 [DOC-MAP.md](./DOC-MAP.md)「README.md」。  
**人读 README 的结构与禁区以本文为准**；实现细节归 `docs/`。

完成标准：读者只靠 README 能 clone、装依赖、跑通最小路径，并知道**项目能做什么、缺什么**；文中无 `docs/` 索引表、无端口/配置/路由这类实现细节。

---

## 读者与边界

README 回答三个问题：**这是什么、怎么装怎么跑、能干什么**。  
`docs/`、`CONTEXT.md`、`AGENTS.md`、ADR 给协作与自动化——不在 README 里当导航表罗列。

✅ 目录树末行：`docs/  # 内部说明，日常使用不必读`  
❌ 开篇「设计原型」下列一串 architecture / adr / 运行手册 / 扩展手册 链接  
❌ 用 README 讲选型取舍（为什么不用 X）、协议细节（CONNECT/ALPN/环形缓冲）

---

## 推荐主线

按序写（可少不可乱序揉段）：

1. **定位**：项目名 + 一行做什么 + 可选能力短标签
2. **页内目录**：介绍 · 项目功能 · 不支持或需要额外条件 ·（未实现功能）· 快速开始 · 怎么工作 · 项目结构
3. **项目介绍**：场景一两段（为什么做、给谁用），不写实现
4. **项目功能**（必有）：`##` 级，列表，见下节
5. **不支持或需要额外条件**（必有）：`##` 级，列表，见下节
6. **未实现功能**（可选，目标态里有、代码还没做时才写）：`##` 级，列表
7. **快速开始**：分阶——Ⅰ 安装 → Ⅱ 配齐完整能力 → Ⅲ 试用 →（Ⅳ 卸载）
8. **怎么工作**（可选）：短流程图 + 2～3 条关键事实
9. **接口用法**（仅当项目对外接口就是 HTTP/SDK 时）：端点表 + 可复制示例
10. **项目结构**：`├──` 树，每项一句

✅ 「项目功能」「不支持或需要额外条件」与「项目介绍」同级：

```markdown
## 项目介绍
…

## 项目功能
- **抓包**：…

## 不支持或需要额外条件
- **只支持 Windows**：…
```

❌ 把功能拆成一堆 `### 功能名` 小标题，每个下面一行——又长又丑  
❌ 并列「配置 / 后端 / 前端 / 一键启动 / 系统依赖 / 使用说明」多节重复同一套步骤

## 项目功能怎么写

**判据：只写核心能力 + 本项目的独特设计。** 同类产品都有的常规操作不算功能。

| 算功能 | 不算功能（不单独列） |
|---|---|
| 产品存在的理由（抓包类：抓包、证书） | 看详情、导出、清空这类每个工具都有的操作 |
| 独特设计（请求列表分类筛选、接口合并、双位置停靠） | 一个视图开关（如「只看成功/只看失败」）——并进所属功能那句里 |
| 只有本项目能做的集成（agent 直接读） | 内部实现（缓存、环形缓冲、并发模型） |

写法：

- 每项一行：`- **名称**：做什么 + 用户得到什么`，控制在两行以内；
- 4～8 条；多于 8 条说明把常规操作当功能写了；
- 不写「缺了会怎样」长表、不写字段/端口/配置；
- 名称用读者熟悉的词，不造新词。

✅

```markdown
- **接口合并**：同一接口（方法 + 完整 URL）反复调用只占一行、行尾标 ×N，点开按时间看每一次——轮询接口不再刷屏。
```

❌

```markdown
- **请求详情**：点开能看到请求头、请求体、响应头、响应体，四块可折叠……
- **成功与失败**：默认 8:2，可切 Default / Success / Error……
```

（这两条都是常规操作/视图开关，不属于「项目功能」。）

## 不支持或需要额外条件怎么写

能力边界，与「项目功能」同级，列表一条一项：

- `- **边界名**：什么情况下受影响 / 需要用户额外做什么`；
- 写清「缺了怎样」和「怎么补齐」，不写成可有可无的装饰；
- 只放能力边界：平台限制、协议限制、需要另一套工具才能覆盖的场景；**计划内、只是还没做的写下一节**。

✅

```markdown
- **Firefox**：需要手动把数据目录里的 ca.crt 导入 Firefox 证书库，否则一直报证书错误。
- **HTTP/2**：只记录 HTTP/1.1，浏览器会自动回落，页面照常。
```

❌ 写成表格；或 `- HTTP/2：不支持` 这种没有后果的短句；或 `- OCR：可选扩展，有则更好`。

## 未实现功能怎么写

目标态里有、只是还没做（或只有留桩）的能力。**不是**能力边界——平台/协议限制、明确不做归上一节。也不是待办清单复读。

- 每项一行：`- **名称**：现在缺什么、缺了会怎样`；
- 指向 `docs/todo.md` 的方向即可，不写验收标准、不写实现方案；
- 全部实现就省略这一节（README 不为「完整」保留空节）；
- 不要把未验证的代码写成「已支持」。

✅

```markdown
## 未实现功能

- **规则改写**：现在只能看，不能改请求或响应；改包要另开工具。
- **HAR 回放**：只能导出 HAR，不能反过来导入重放。
```

❌

```markdown
- [ ] 实现改写（验收：抓到 https://… 能替换响应体）
```

## 硬规矩（对 / 错）

### 自洽：关键用法写在正文

跑通最小路径需要的命令、入口 URL、必须填的环境变量写进 README。

✅ 「`uv sync`，然后 `uv run python start.py`，打开 http://127.0.0.1:5173」
❌ 「字段见接口手册」「验收见运行手册」代替正文

### 扩展：写清「缺了缺什么」

需要额外配置才能完整的能力，用「配好了能做什么 / 没配时」表述，不写成可有可无装饰。

✅ `- **OCR**：独立图片的文字转写；没配时图片几乎只剩元信息`
❌ `- **OCR**：可选扩展，有则更好`

### 实现细节不进 README

端口默认值、数据目录结构、配置字段表、HTTP 路由表、协议细节一律写进 `docs/`（通常是 `docs/pipelines.md`）；README 最多留一句指针。

✅ 「代理默认 `127.0.0.1:8899`；要改端口或上限见 `docs/pipelines.md` 的『配置与数据目录』」
❌ README 里贴 `cordis.patch.yml` 片段和 9 行配置表、10 行路由表

### 远程与事实

远程仓库写**当前真实 clone URL**；变了再改。生产/本地入口写真实地址。

✅ `远程仓库：https://gitee.com/org/repo.git`
❌ `GitHub：无（当前远端在 Gitee）`

### 健康检查与调接口

健康检查、试接口：浏览器打开文档/健康 URL，或 `curl`。

✅ `打开 http://127.0.0.1:8020/docs`
❌ 把 `Invoke-WebRequest …` 写成项目标准调试姿势

### 结构用树

✅

```text
myapp/
├── start.py
├── backend/
└── frontend/
```

❌ 扁平「路径 + 说明」长列表，或再贴一张 import 链当结构

### 删重复与实现废话

与上文已写过的入口 URL、步骤不要再写「确认」段。代理、中间件等实现细节不进 README。

✅ 生产信息表里已有健康检查 URL → 启动节不再抄一遍
❌ 启动后再贴一段 PowerShell 健康检查；或「前端把 `/api` 代理到后端」类实现说明

### 不写进 README

- 未验证方案、对照实验清单 → 计划类文档
- 会随需求常变的前端交互边界 → 有则 `DESIGN.md` / 目标架构文档
- 术语定义、ADR 全文、给 AI 的禁令 → 各自文件，README 不索引
- 选型取舍（为什么不用 X）→ `docs/adr.md`

## 落笔步骤

1. 认读者路径：最小可跑要几步；完整能力还要哪几步。
2. 定「项目功能」清单：先写核心能力，再挑 1～3 个独特设计；常规操作删掉。
3. 补「不支持或需要额外条件」；目标态有而未做的放进「未实现功能」（没有就不开节）。
4. 按「推荐主线」起草或改写；能合并的重复节删掉。
5. 对照本文硬规矩逐条过一遍（尤其：三节同级用 `##` + 列表、无表格、无实现细节、远程 URL、健康检查方式、树形结构）。
6. 自己当陌生人扫一遍：只读 README 能否装好并跑通 Ⅰ；能否说出「它能干什么、缺什么」。

完成标准：第 5、6 步无未改问题；非对外 API 的项目，README 内无配置表/路由表/端口表；功能清单里没有常规操作。
