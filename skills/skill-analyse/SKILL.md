# 分析 Skill 项目

读一个 skill 仓（或含 `SKILL.md` 的目录），写出给人看的分析报告。范本：仓库根 `analyse/skill-context-doctor.md`。

## 何时用 / 何时不用

**用**：用户说 `/skill-analyse`，或要分析某个 skill 项目、写 analyse 报告。

**不用**：

- 新建或改本仓个人 skill、删 skill、找上游 skill → `skill-crud`
- 写 agent 会读的规范 / description → `skill-crud/references/style.md`
- 写 笔记库 主题文 → `self-notes-read`
- 从本轮开发抽面试题 → `session-tools`

---

## 落盘

默认写入技能仓根目录：

```text
analyse/<skill名>.md
```

- `<skill名>` 用上游包名或目录名（去 `-main` / `-master` 后缀），如 `skill-context-doctor`。
- 用户指定了路径就用指定路径。
- 已有同名报告则改写，不平行再开一篇。
- 报告是给人读的分析，不是 笔记库，也不是 `SKILL.md`。

文头只留来源一行，不要写归纳日期、不要写「外部文档」：

```markdown
> 来源：https://github.com/org/repo
```

无公开上游时写本地仓路径或省略该行。

## 报告骨架（固定五块）

按序写，章名固定为下面这些（可改编号前缀，不可拆并乱序）：

### 标题下简介（两段）

1. **功能段**：只写这个 skill 做什么、默认行为边界。不写本机副本路径、本仓版本号、本机目录。
2. **背景段**（可选）：前身、从什么问题改成什么问题。另起一段，不塞进功能段。

### 1. 安装与命令

- 怎么装（`npx` / `npm i -g` / 拷贝 skills 目录等，以该项目 README 为准）。
- 表：命令 → 作用。默认 dry-run 的要写明须 `--apply` 才改盘。
- 不要用「项目地址」当章名；地址若有，放进「来源」或安装说明里一行即可。

### 2. 源码结构

- 入口文件怎么进主流程。
- 浅层目录树 + 每个关键文件一句话职责。
- 默认扫描/安装根若影响理解，可列在本节末。

### 3. 核心原理

- 主链路（伪代码或调用链）。
- 关键判定、证据分档、规则表等「为什么这样」；只写读源码能站住的。
- 易混点单独小节（例如「HIDE 不是删 description」）。

### 4. 原理举例

必须按**第一步 → 第四步**（或该项目真实阶段数）写清，不能只列结论表。

参考范本节奏：

1. 它先看见/加载什么  
2. 它去哪找证据/输入  
3. 它怎么判定/打分  
4. 它动手时实际改什么  

举完后可加「你以为 / 实际」对照表。用户若已在对话里纠正过理解，把纠正写进举例或对照，不要只留抽象规则。

---

## 步骤

1. 定位目标：用户点名的仓路径、GitHub URL，或当前打开的 skill 目录。
2. 读 README / `SKILL.md` / 入口与设计文档；需要时再读核心模块源码。事实以源码为准，README 只作线索。
3. 按「报告骨架」起草；对照范本 `analyse/skill-context-doctor.md` 查缺漏（尤其举例是否分步、简介是否掺了本机信息）。
4. 写入 `analyse/<skill名>.md`。聊天里只报：分析了谁、落在哪；不要把全文再贴一遍。

---

## 完成标准

- 文头只有来源（或明确无上游）
- 简介功能段无本机路径 / 本仓版本；背景另段
- 五块齐全：简介、安装与命令、源码结构、核心原理、分步举例
- 举例按步骤写，含「判定后实际改什么」
- 文件已写到约定落盘路径
