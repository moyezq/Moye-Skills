# 会话交接

交接的是**状态**，不是对话。仓库、文件、跑过的验证是**事实源**；对话历史和交接文档都是**简报**，都可能过期，冲突时以仓库为准。

先判走哪条：

| 手上这件事 | 走 |
|-----------|-----|
| 要写一份交接，留给下个会话 | §2 起 |
| 上个会话留了交接，接着干 | §5 |
| 用户没提，但会话在绕圈 | §1 最后一条 |

---

## 1. 先判该不该写文件

窗口快满是感觉，不是判据。判据是**这段历史还有没有用**。三条路，选一条说清：

- **继续原样**：同一件事、历史还在帮忙、窗口够用。不写文件，接着干。
- **续原会话**：想连历史一起留着 → DSH 终端 App 支持 `--resume <id>`（前提是装了对应 profile）。本机没查到 `/compact` 一类的就地压缩，压缩这件事由这份交接承担。
- **写交接，开新会话**：用户要干净上下文；会话被反复纠正过（同一个坑改了三遍）；关键假设中途变了；一大阶段收尾而后续还有活；模型开始复述自己、绕圈。

一段会话里跑着多条工作线时，别只交主线，每条各写一段状态。

用户没提交接、但你已经看出这套信号 → 主动提一句「建议交接后开新会话」，别默默写文件。

**交完即止**：写完交接就停在这个阶段边界上。交了再接，第一份交接会在十几步内过期、还得再写一份。
要接着干就先说清「本会话继续」；否则把写交接当作收尾动作，下个会话再接。

**完成标准**：一句话说得清选了哪条、为什么。

---

## 2. 收集事实，不凭记忆

按序查，全部用工具查（非 git 工作区跳过其中 git 那几条）：

- `git branch --show-current`、`git status`（含未跟踪）、`git diff --stat`
- 本轮跑过的验证：命令名 + 真实结果。这是「验证状态」栏的唯一来源。
- 正在改的文件与符号：用 `grep` / `read` 确认路径和符号真存在。
- 项目自己的文档：`CONTEXT.md`、`AGENTS.md`、`docs/adr.md`、`docs/architecture.md`（读到什么算什么，按 `self-project-docs`）。
- 写进正文的**数字**（数量、行号、用例数、清单项）：写之前用工具数一遍（`grep`、真跑一次、`--collect-only` 之类）；代码或清单变了，**同一轮**改数字。旧数字留在文件里比从没写过更坏——它在替你说一件你已经否掉的事。
- **进程 / 产物当前状态**（服务在不在、跑完没有、库与源一致不一致）：每句带当轮实测命令与读数，并写清何时量的；量不出来的当场标「未核实」，不写成既成事实。这类断言过期最快：写「已完成」时它可能还在跑，写「137 一致」时源已经变成 138。

| 你要写的话 | 用它证明 |
|---|---|
| 「进程跑完了」 | `Get-Process python \| Select-Object Id,StartTime,CPU`——列不到才算跑完；列得到就连 pid 与 CPU 读数一起写 |
| 「产物在这一步落盘了」 | `Get-Item <文件> \| Select-Object LastWriteTime,Length`——读数写进正文 |
| 「库与源一致」 | 真跑一次对账脚本（`verify_ingest.py` 这类），exit code 与两边计数都写进去 |

**完成标准**：每条要写进交接的路径、符号、命令、数字，都刚被工具确认过。

---

## 3. 三清单：不许只活在对话里

这一节是交接质量的分水岭。列三张清单，逐条落地：

1. **用户做过的决定**（用他自己的话）：定的数字、改的规矩、否掉的方案、搁置的事、一句「行」。扫全对话，含中途插话和单词回复。
2. **会话自己发现的缺陷与开放问题**：你查出来、说出来，但没人要求你记下来的那些。这张通常最长，也最容易被跳过 —— 在对话里说清楚不等于记下来了。
3. **前后改口过的数字**：先说 A 后改成 B 的参数、阈值、路径、版本。旧值留在文件里比从没写过更坏：文件在替你说一件你已经否掉的事。

每条问一句：**哪个文件承载它**？然后 `grep` 证明它真在那。只活在对话里的，现在就写进承载它的文件：

- 长期叫法、决策、模块状态、端口入口 → 走 `self-project-docs` 的对应文件
- 本轮工作态 → 写进本次交接正文（§4）

**完成标准**：三张清单每条都指得出文件，且 grep 得到；指不出文件的那条就是还没落地。

---

## 4. 写交接：一个指针，一份活着的交接

**落点**：

- 正文 `docs/handoff/HANDOFF-<YYYY-MM-DD>-<slug>.md`，slug 取 2–4 个英文小写词
- 指针 `docs/HANDOFF.md` —— 固定名，唯一入口，永远指向活着的那份正文
- 非仓工作区（普通项目目录）→ 正文 `handoff/`，指针放工作区根 `HANDOFF.md`
- 仓库已有交接约定 → 沿用已有的

正文首行和指针文件里都写一句：`> 临时工作态，不是项目文档；长期规矩见 CONTEXT.md / docs/adr.md`。

**正文模板**（照这个写）：

```markdown
# 交接：<一句话目标>
**写于**：YYYY-MM-DD HH:MM ｜ **分支**：<branch> ｜ **状态**：进行中 / 等用户决定 / 收尾

## 目标与验收标准
## 已完成
（区分「已实现」与「已验证」）
## 关键决定与理由
## 否决的路线
（每条一句理由 —— 重复走死路最贵）
## 相关 / 改动的文件
（路径 + 符号 + 为什么重要）
## 剩余工作
（有序）
## 已知问题 / 开放问题
## 验证状态
（跑过的命令名 + 结果结论；只写真跑过的）
## 完成判据
（做完能看到什么）
## 下一步
（单条最佳起手动作）
```

**写法**：

- 引用路径、符号、命令，不贴大段代码、不贴 diff。
- 不写密钥、token、`.env` 值、私有 URL。
- 「下一步」要让执行者自己判断成败：让人跑命令时，连「怎么看出问题 / 失败在哪一步 / 期望输出与耗时量级」一起写。
- **不写提交流水与时间线**：代码都已提交到远端，新会话只需要**最新状态**；「什么时候提交了什么」对下一个会话没有指导作用——要历史用 `git log`。
- **过期即删，同一工作线只留一份正文**：过时或被推翻的内容当场删掉（旧数字、已经做完的「下一步」、只在当时那次运行里才有效的进度）。老的正文不要按日期堆在 `docs/handoff/` 里当历史——历史在 git 里，堆在目录里只会让新会话读到互相矛盾的旧状态。
- 宁长勿短。这份文件占的上下文相对整个窗口可以忽略，欠写要下个会话花几小时重查。目标 150–400 行。
- 指针文件只放：正文文件名、写于、一句话目标、下一步，加一行「正文过期以本指针为准」。

**写完回读**：`read` 一遍正文，对着 git 现状核对，再声明它好了。

**完成标准**：指针指向的正是刚写那份；正文里每条断言都指得到出处。

---

## 5. 接续：新会话怎么开工

按序：

1. 确认工作区与分支（`git branch --show-current`、`git status`；非 git 工作区跳过）。
2. 读 `docs/HANDOFF.md`（或工作区根 `HANDOFF.md`），再读它指的正文。
3. 按 `self-project-docs` 读项目自己的文档。
4. **核对，不轻信**：交接里点到的文件、符号、命令逐个 `read` / `grep` 确认。仓库与交接冲突时以仓库为准，差异记下来。
5. 给一段简短复述：已完成、剩下的、差异或疑问、下一步。
6. 从「下一步」接着干 —— 除非用户只要一份现状说明。

**完成标准**：关键断言都核对过，差异已说给用户。

---

## 6. 交接不是项目文档

交接会过期，项目文档不会。出现下面这些，当场提升出去，交接里只留指针：

- 长期叫法、决策、模块边界、端口入口 → `self-project-docs`
- 一条反复要用的命令、一个稳定的坑 → `README.md` / `AGENTS.md`

同一份工作只留一份活着的正文与一个指针。**过期的正文要清理，不要按日期堆积**——堆积的旧正文会被新会话当成现状读，而里面全是旧数字与早已做完的事；要历史去 `git log` 取。清理时先把仍有效的经验（规矩、坑与解法）并进活着的那份正文，再删。

---

## 7. 交接提示词（本 skill 最后的输出）

写完交接，最后给用户一段能直接粘贴的提示词，**以用户口吻写**：用户是「我」，助手是「你」，别用第三人称称呼用户。

- 个人 skills 开场自己会加载，别把那些规矩再抄一遍 —— 重复一份就会漂，而提示词这份没人维护。
- 只写三件事：读哪个文件、照验证状态先核实、从下一步开始。
- 两三句，别写成第二份交接。

```text
我上个会话的交接在 docs/HANDOFF.md，先读它和它指的正文，对着仓库核对里面的断言，然后从「下一步」接着干。有对不上的地方先跟我说。
```

**完成标准**：用户能原样粘进新会话，一个字都不用改。
