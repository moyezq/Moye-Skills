# ADR 格式

ADR 放在 `docs/adr/`，用递增编号：`0001-slug.md`、`0002-slug.md` ……

`docs/adr/` 目录按需懒建：第一条 ADR 需要时才建。

## 模板

```md
# {决策的短标题}

{1-3 句：背景是什么、决定了什么、为什么。}
```

就这些。一条 ADR 可以只有一段。价值在记录「**做**了某个决策」和「**为什么**」，不在填满各节。

## 可选节

只在真能增值时才加，多数 ADR 不需要：

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：决策会被推翻时有用
- **Considered Options**：只有被否掉的备选值得记住时
- **Consequences**：只有不明显、需点明的下游影响时

## 编号

扫 `docs/adr/` 找最大编号，加一。

## 何时建议记 ADR

三条同时成立：

1. **难逆转**：日后改成本有意义
2. **没上下文会费解**：未来读者会看着代码想「为什么偏要这么做？」
3. **真实权衡的结果**：有真实备选，为具体理由选了其一

好逆转就跳过（你会直接逆转）；不费解就没人会问；没有真实备选就只剩「我们做了显而易见的事」，无记录价值。

### 什么够格

- **架构形状**：「用 monorepo。」「写模型事件溯源，读模型投影进 Postgres。」
- **上下文间的集成模式**：「Ordering 与 Billing 靠领域事件通信，不走同步 HTTP。」
- **带锁定的技术选型**：数据库、消息总线、鉴权提供方、部署目标。不是每个库，只是那些换个要花一个季度的。
- **边界与范围决策**：「客户数据归 Customer 上下文，其它上下文只按 ID 引用。」明确的「不做什么」和「做什么」同样值钱。
- **对显而易见路径的刻意偏离**：「用手写 SQL 而不是 ORM，因为 X。」合理读者会假设相反的任何事。这些能阻止下个工程师「修复」一个刻意为之的东西。
- **代码里看不见的约束**：「合规要求下不能用 AWS。」「合作方 API 契约要求响应 <200ms。」
- **不明显的被否备选**：考虑过 GraphQL 却因微妙理由选了 REST，就记下来；否则半年后有人又提 GraphQL。
